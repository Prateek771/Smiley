# Phases 3–10 Implementation Plan

> **For agentic workers:** Use test-first execution with independent bounded UI/schema/runtime preparation and a fresh whole-branch review. The owner explicitly authorizes continuous execution through Phase 10; routine choices and passing promotions do not need new approval prompts.

**Goal:** Complete and verify the local staff/case/private-document foundation through Phase 10.
**Architecture:** Preserve the public synthetic demo; add a separate protected desk backed by reviewed PostgreSQL/Drizzle tables and Better Auth. Enforce ownership/role/branch context in services and non-owner database RLS, with immutable event/document history.
**Tech Stack:** Node.js 24+, Next.js 16.3.8, TypeScript, Tailwind, PostgreSQL 17, Drizzle, Better Auth, Playwright Test, tsx + node:test.
**Spec:** [Desk foundation design](../specs/2026-10-01-phases-3-10-design.md), [Phase 2 contract](../specs/2026-10-01-cashless-discharge-design.md).

## Global constraints

- Work on dev; promote only tested checkpoints to main. Retain local recovery refs privately.
- Synthetic records/files only; no cloud provisioning, email sending, payer integrations or real data.
- PostgreSQL name sehospitaldb; preserve all 42 domain tables and four source reporting views. Review changes before migration; never execute source DROP DATABASE scripts.
- Server session validation and current staff access on every protected route. Untrusted client tenant/owner assertions never grant access.
- Money uses integer paise/exact decimal strings; unknown values stay nullable. AI/money/payer approval workflows remain later phases.
- File types PDF/PNG/JPEG/UTF-8 text; maximum 5 MiB; private generated storage keys; no public files.

## Review focus

1. Old or removed staff sessions cannot use API/download routes after access is revoked.
2. Same-hospital wrong-branch and cross-patient linkage are denied, including direct database operations as the application role.
3. Future demo evidence/acknowledgement never leaks through an earlier checkpoint.
4. Concurrent/stale/idempotency-conflicting actions cannot lose changes or duplicate audit/document revisions.
5. Upload failures, misleading MIME/filenames and unauthorized revision downloads produce no partial records or exposed paths.
