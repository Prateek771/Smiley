A patient may have encounters in more than one branch of the same hospital; that does not allow a claim in one branch to borrow an encounter in another.

The table below retains every source domain table. “Global reference” means a curated catalog that ordinary hospital users can read but cannot administer. The source therefore permits the failure examples in this table. Proposed target UNIQUE keys below are additions beyond the five conversion repairs; they exist to support scoped composite FKs.

## Database role, RLS and transaction strategy

Use distinct migration-owner, application, auth-adapter and future worker privileges. The application role must be a non-owner, `NOSUPERUSER`, `NOBYPASSRLS`, unable to alter schema/policies or run ordinary DELETE/TRUNCATE on operational history. Grant only required tables/actions/sequences. Keep schema ownership/migration credentials out of application connections. Protect authorization tables from ordinary self-grant writes.

Enable and force RLS on tenant operational tables when Phase 7 enforces access. Bind both visible-row `USING` and inserted/updated-row `WITH CHECK` conditions to authenticated hospital scope, exact eligible branch and active role grants. Missing context or revoked grants denies access. Table owners, superusers and BYPASSRLS roles have special bypass behavior; referential integrity checks are separate from access controls. Therefore every integration test must exercise the actual application role, not the migration owner. [PostgreSQL row-security documentation](https://www.postgresql.org/docs/16/ddl-rowsecurity.html) describes those boundaries.

The server verifies the Better Auth session, resolves its domain user, checks hospital/branch/role authorization, begins a transaction, sets parameterized transaction-local `app.hospital_id`, `app.branch_id` and `app.user_id`, and performs all ORM reads/writes on that transaction's connection. Commit/rollback ends the context. Do not set session-level context on pooled connections, execute queries outside the scoped transaction, or trust tenant/actor values from a request body alone. `SET LOCAL` and `set_config(...,true)` are transaction-local approaches. [PostgreSQL SET documentation](https://www.postgresql.org/docs/16/sql-set.html) supports that pool-safe lifetime.

Custom settings are context, not authentication. A compromised server or unrestricted SQL client with application credentials can change them. This strategy protects against accidental unscoped queries and reinforces server authorization; it does not make an untrusted direct database client an authenticated staff member. Keep credentials server-only. Membership RLS lookups must avoid recursive policy loops; prefer a simple indexed lookup or a narrowly scoped private SECURITY DEFINER helper with an immutable search path, explicit actor/context checks and restricted execution, reviewed when implemented. Do not add a helper that accepts an arbitrary user and exposes another hospital's grants.

Global catalogs use read-only application grants; auth tables have server-only adapter permissions and no hospital query endpoints. Hospital/branch admin capabilities and support access are separate from ordinary staff actions. Jobs, private downloads, exports and reporting must reuse the same scope rules when those phases appear. Structural scoped keys land in Phase 5; authenticated policy/action enforcement and runtime negative tests land in Phase 7 before any real access is enabled.
