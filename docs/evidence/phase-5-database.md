# Phase 5 — reviewed PostgreSQL database layer

Verified on 2026-10-01 against the approved local PostgreSQL 17 synthetic runtime. No source bootstrap SQL was executed, and no database was dropped or truncated.

## Result and scope

The target retains all 42 business tables inventoried in `docs/schema/domain-inventory.json` and exposes four `security_invoker` views. Ten infrastructure additions bring the target to 52 tables: `auth_user`, `auth_session`, `auth_account`, `auth_verification`, `branches`, `user_branch_memberships`, `staff_invitations`, `claim_events`, `document_revisions`, and `document_evidence`. Graphile Worker and AI storage remain deferred.

`src/server/db/schema.ts` contains the repaired domain/operational definitions. `auth-schema.ts` uses Better Auth's expected camelCase properties over snake_case SQL columns. The legacy domain `users.password_hash` is omitted from the target; `users.auth_user_id` is a unique foreign key to `auth_user`, and active staff identities must have that mapping. Hospital roles and individual branch role grants remain domain records.

The three additive migrations are `0000_reviewed_foundation.sql`, `0001_case_version_and_identity.sql`, and `0002_numeric_and_audit_constraints.sql`. The first creates the reviewed tables, indexes, constraints, timestamp/history triggers, and four views. The second adds optimistic case versioning, next action/due date, request fingerprint/idempotency fields, and the active identity invariant. The third closes the special-numeric-value and nullable branch-log attribution gaps found in independent review. Snapshots and the migration journal are checked in with these migrations; later phases must append migrations rather than edit an applied file.

## Repairs enforced by PostgreSQL

- All 52 source enum columns have CHECK constraints containing the inventoried allowed values. The five invalid converted UNIQUE declarations are valid named uniqueness constraints, and all eight lost source indexes are restored.
- Identity fields use `GENERATED BY DEFAULT AS IDENTITY` without a column default. The Phase 4 parser originally misread the word `DEFAULT` in the identity clause as `DEFAULT AS`; its interpreted inventory metadata is corrected while preserving raw source definitions and hashes.
- Source timestamps use `timestamptz`; five source `updated_at` fields are maintained by database triggers. Date-only fields remain dates.
- INR amounts remain exact `NUMERIC` rupee values returned as strings. Unknown nullable amounts remain `NULL`, and monetary values cannot be negative. Percentages are bounded to 0–100. All 46 numeric columns explicitly reject NaN and positive/negative infinity. Domain IDs remain PostgreSQL bigint and are returned as decimal strings by the seed helper.
- Operational descendants include hospital/branch scope. Composite foreign keys require memberships, encounters, claims, submissions, documents, invoices, and actors to belong to the same owner and case. An invoice's non-null encounter must also equal its claim's encounter; constraint triggers enforce both invoice writes and later claim encounter changes.
- Branch memberships require a user role in the same hospital; roles are granted separately for each branch. Invitations have `PENDING`, `ACCEPTED`, and `REVOKED` states. Acceptance keeps a pending row locked until the final accepted write in later service code.
- Claim events, audit logs, document revisions, and document evidence reject UPDATE/DELETE through history triggers. Evidence-bearing parent relationships use RESTRICT. Event idempotency keys and document revision/idempotency/storage keys are unique at their intended grain.
- Audit/login records may omit hospital and branch for system events, but a non-null branch requires a non-null matching hospital. Actor attribution separately requires the actor's hospital.

## Runtime and seed interfaces

`client.ts` exports `appPool`, `migrationPool`, `db`, `loadEnvironment()`, and `closePools()`. Environment loading reads ignored `.env.test.local` for `NODE_ENV=test` and `.env.local` otherwise, without logging secrets. Pool construction is lazy. The application pool uses the non-owner `smiley_app` role; schema migration and synthetic provisioning use `smiley_migrator`.

`migrate.ts` exports `migrateDatabase(pool?)`. It serializes migration runs with an advisory lock, rejects existing untracked application tables even if an empty tracking table exists, verifies the hashes of applied files, and applies only pending migrations. Its application grants allow auth lifecycle and required operational writes, deny clinical/evidence DELETE, deny global catalog INSERT/UPDATE, and deny immutable-history UPDATE. Row-level policies are implemented in Phase 7; these grants alone are not a tenant isolation boundary.

`seed.ts` exports `seedSynthetic(pool?)` and returns stable decimal IDs for `hospitals.a/b`, `branches.aCentral/aNorth/bCentral`, role codes, patients/memberships/encounters, and the fictional payer/policy. It preserves existing rows through conflict-safe inserts. It requires an explicit loopback migration URL whose database matches `current_database()`, permits only `sehospitaldb` or a database ending `_test`, and refuses a hospital database containing non-`SYN-` codes. The configured host is checked because PostgreSQL sees Docker's bridge address despite the verified host binding to `127.0.0.1:5442`.

Four reviewed source master INSERT groups seed 9 categories, 35 subcategories, 9 original roles, and 6 workflow definitions. `FINANCE_OFFICER` is added as approved. The operational fixtures comprise `SYN-A`/`SYN-B`, branches `A-CENTRAL`/`A-NORTH`/`B-CENTRAL`, fictional insurer/plan records, and synthetic patients, memberships, and encounters. Authentication credentials are provisioned in Phase 6, not printed by the database seed.

CLI wrappers are `scripts/db-migrate.ts` and `scripts/db-seed.ts`. They close pools and report failures without exposing connection strings or passwords.

## Verification evidence

The first test ran against a genuinely empty guarded `sehospitaldb_test`: the expected 52-table inventory failed with actual count 0 before implementation. During the first real apply, a generated redundant branch uniqueness column was rejected; the transaction left no public tables or applied ledger rows. The generator was corrected and the unapplied migrations were regenerated before their successful application. No applied migration was rewritten.

The fresh-path test applied only migration 0000, seeded records, inserted `SYN-MIGRATION-PRESERVATION` with exact claimed amount `123.45`, and confirmed the version column did not yet exist. Applying 0001 preserved that amount and populated version 1. Subsequent full targeted runs passed **12/12** tests. A too-long synthetic hospital code in one negative test was shortened so it exercised the intended enum CHECK rather than the VARCHAR length limit.

The suite covers migration/seed idempotence; 42 source table/column retention; 52 enum allowed sets; eight source indexes; four invoker views; invalid lifecycle/percentage/negative money rejection; five duplicate uniqueness grains; cross-hospital, wrong-patient, wrong-membership and wrong-branch case links; submission/workflow case consistency; invoice/claim encounter consistency; unique auth mapping and branch role ownership; immutable events/audit; event idempotency; evidence-preserving parent deletion; all five timestamp triggers; and application-role ownership/privilege checks. Test mutations use rollback transactions and expected-denial savepoints. Tests require explicit `_test` connection URLs and never reset an existing database.

Independent review reproduced two structural gaps with PostgreSQL writes: `NaN` passed existing nonnegative amount/positive quantity checks, and both audit/login logs accepted a branch while hospital and actor were null because nullable composite foreign keys use MATCH SIMPLE. Two new rollback tests failed for those reasons before the repair. Migration 0002 adds exactly 46 finite numeric checks and two branch-to-hospital attribution checks. Snapshot 2 was compared structurally with snapshot 1 and differs only by those 48 additional CHECK constraints; the generated SQL contains only 48 `ALTER TABLE ... ADD CONSTRAINT ... CHECK` statements. Applied migrations/snapshots 0000 and 0001 were not edited.

After applying 0002, the final suite passed **14/14** tests against the primary synthetic test database and **14/14** against the retained restore database. The numeric test performs real NaN writes for both a claim amount and service quantity, inventories finite checks for every numeric base-table column, and confirms nullable unknown amounts remain accepted. The attribution test verifies rejection for both logs and accepts matching hospital/branch and system-level events. The migration preservation sentinel still contains `123.45` and version 1.

When a database is already tracked, the suite seeds or preserves its synthetic sentinel with `ON CONFLICT DO NOTHING` and reports that it is testing a repeat/idempotence path. That path does not claim to prove an empty-database additive migration; the fresh path was verified separately and remains available for the CI fresh-database step.

## Backup and isolated restore

The container `smiley-dev-postgres` was rechecked as running with label `com.smiley.local-runtime=synthetic`. Using the approved local bootstrap role, the test database was backed up with `pg_dump --format=custom --no-owner --no-privileges` and restored with `pg_restore --role=smiley_migrator --no-owner --no-privileges` into the newly provisioned disposable database `sehospitaldb_restore_86dc69215a924c6d99dcbcdcdb881c57_test`.

The restore contained **52 tables, four security-invoker views, 415 constraints, and two migration ledger rows**. Actual row counts for all 52 public tables matched the source. The sentinel remained `123.45` with version 1. Constraint names, values, and operators matched after ignoring PostgreSQL's equivalent cast decoration/parentheses/whitespace introduced by dump/restore. The entire 12-test suite then passed against the restored database, checking the restored constraints through real writes.

The restore database and `/tmp/smiley_phase5_86dc69215a924c6d99dcbcdcdb881c57.dump` in the synthetic container are retained for review. Database roles/grants are provisioning concerns and were intentionally excluded from the dump; the migration helper reapplied the application's required privileges during restore testing.

The retained dump proves the initial 0000/0001 checkpoint. The restored database was subsequently upgraded through additive migration 0002 and passed the final 14-test suite, preserving the sentinel; it now has 463 constraints and three migration ledger rows. The dump itself was not replaced or represented as a later checkpoint backup.
